### Notes

- **abuse.ch auth-key change is real and confirmed**: as of 2025 all three abuse.ch APIs (URLhaus, ThreatFox, MalwareBazaar) require an `Auth-Key` HTTP header, obtained free at `auth.abuse.ch`, shared across all three services. Do this signup on day 1 — it's the single most valuable IOC source for this build and the only one with a hard blocker if skipped. SSLBL and Feodo Tracker's **bulk CSV/JSON blocklist downloads** are the exception — those remain fetchable without a key, only the interactive query APIs need it. Verify exact current requirement at build time since abuse.ch has tightened auth before and may again.
- **JA3 ecosystem is genuinely dead, JA4 is where the community is**: confirmed the Salesforce `ja3` repo was archived 1 May 2025 and ja3er.com is unreachable (corroborated by a GitHub issue thread and Fastly's own TLS-fingerprinting research, which separately flags ja3er's *historical* data as unreliable even before it went down). The only living public malicious-JA3 list found is **abuse.ch SSLBL's JA3 blacklist** (built from malware PCAPs, still generated every 5 min). For anything beyond blacklist-matching, JA4DB (ja4db.com, FoxIO) is the actively developed successor — but the project spec says "JA3 (planned)", so flag this mismatch to the team: building against JA3 means building against a fingerprint standard whose only public infra is one abuse.ch list.
- **Domain whitelisting > blacklisting confirmed as the higher-value move**, per the task's own framing. Verified three ensemble-able popularity lists are all currently live (checked via direct HTTP HEAD during this research, same-day Last-Modified on all three): Tranco, Cisco Umbrella top-1M, Majestic Million. Recommend **Tranco alone** if only one is used (it's explicitly built to resist manipulation of any single input list, including Umbrella and Majestic which it ingests) — using all three adds robustness but is not necessary for a hackathon MVP.
- **MaxMind vs DB-IP**: MaxMind GeoLite2 remains free but registration friction has measurably increased (90-day key expiry, phone verification) — budget setup time or skip it. **DB-IP Lite (CC-BY, no account, MMDB format)** is the pragmatic choice for a 5-day build: same library ecosystem (`maxminddb` Python/Go/etc. readers work on both), zero signup friction, monthly updates are plenty for GeoIP-grade accuracy needs.
- **MISP verdict**: treat MISP as a *format and feed-catalogue* reference, not infrastructure to deploy. Standing up MISP (AGPL, PHP/MySQL/Redis stack, workers, background jobs) inside a 5-day hackathon build is disproportionate to the value it adds over directly consuming the same free feeds (abuse.ch, Tor, Feodo) that MISP itself re-publishes.
- **PCAP corpora**: for the specific attack classes NetForensiq targets — C2 beaconing, DNS tunnelling, exfiltration, port scan — the best match is **malware-traffic-analysis.net** for beaconing/malware delivery (small, individually-labeled, real malware), **CICIDS2017/2018** for port-scan/DoS/brute-force with labeled flow CSVs, and **Netresec's MACCDC captures** for port-scan/lateral-movement in a red/blue-team context. DNS tunnelling specifically is under-represented in all of the above — ⚠️ UNVERIFIED whether any of these corpora contain labeled DNS-tunnelling traffic; may need to synthesize test traffic (e.g. `iodine` or `dnscat2` in a lab capture) rather than relying on a public dataset for that detector.

### Notes

- **This section is deliberately sceptical, per the task brief, and the scepticism is now backed by direct evidence, not just absence-of-search-results.** The one hard technical confirmation obtained — CCTNS/ICJS requiring **firewall-cleared point-to-point network links on ports 443/80 per pilot location**, with central dashboard access restricted by name to NCRB/NIA/NCB/CBI — is a strong, citable data point (sourced from an MHA integration PDF) that these systems are not internet-reachable APIs under any circumstance, let alone something a hackathon team could self-serve.
- **Only two genuinely public, documented APIs found in Indian government infrastructure relevant to this space**: (1) **data.gov.in's OGD platform**, which is real and has actual cybercrime-adjacent statistical datasets (verified URLs above), and (2) **DigiLocker/APISetu**, which is real but partner-gated and not well-matched to NetForensiq's forensics use case anyway.
- **Sanchar Saathi / Chakshu / CEIR / NCRP / 1930 / CERT-In / NCIIPC / CSK**: no public API or machine-readable feed found for any of them after direct searches and (for CERT-In) a direct site fetch. These should all be treated in the hackathon pitch as **reference/context systems to cite, not systems to integrate with** — e.g., "NetForensiq's evidence export format is designed to be compatible with what CCTNS/ICJS would eventually expect" is a defensible, honest framing; "NetForensiq connects to CEIR" is not, absent further evidence.
- **CEIR is the one item left at ⚠️ UNVERIFIED rather than a flat "no"** — because CEIR's function (cross-operator IMEI blacklist sync) *structurally requires* some kind of API between DoT/C-DoT and telecom operators; it plausibly exists but is operator/DoT-internal and not documented anywhere publicly findable. Do not assume it, do not build against it; if the team has an actual police/DoT contact, that's the only way to confirm.

### 3d. Should NetForensiq expose itself as an MCP server?

**The idea**: let an analyst's LLM client (Claude Desktop, etc.) query NetForensiq's own flow/detection database directly — "show me all flows from this IP in the last hour," "summarize today's high-confidence C2 detections" — via a NetForensiq-authored MCP server sitting in front of its Postgres/analysis backend.

**Pros:**
- Natural fit for the analyst-review workflow this spec's Part 4 is about — triage-by-conversation is a genuinely useful UX for a SOC analyst, and MCP is a reasonable, standardised way to build it rather than inventing a bespoke chat-plugin protocol.
- Cheap to demo: MCP servers are typically a thin JSON-RPC wrapper over existing internal APIs, so if NetForensiq already has a REST/query layer, the MCP server is mostly boilerplate — could be a good bonus-points/differentiation feature for judges familiar with MCP.
- Read-only, scoped tools (e.g. `get_flow(id)`, `list_high_confidence_detections(since)`) are a much smaller attack surface than a general database MCP server like the archived Postgres one.

**Cons (the obvious security objection, stated plainly as asked):**
- **This is law-enforcement case data.** Wiring it into a general-purpose LLM client means every query and every returned flow/IP/domain/detection potentially leaves the forensics environment and transits through whatever LLM backend the analyst's client is configured to use — a real data-exfiltration and chain-of-custody concern for material that may become court evidence. Anything that touches evidence integrity (this repo's own `SPEC_01_EVIDENCE_INTEGRITY.md` is presumably the place this gets reconciled) needs the MCP layer to be either fully local/air-gapped (a local model, not a cloud LLM) or explicitly excluded from evidentiary data and limited to non-evidentiary operational views (e.g. dashboard summaries, not raw packet/flow records tied to a case).
- **Prompt-injection risk is not hypothetical here**: flow metadata NetForensiq would expose — TLS SNI, HTTP Host, DNS query names — is attacker-controlled text. If those strings are ever fed back into an LLM's context (e.g. "summarize this flow" including a malicious SNI value crafted to contain prompt-injection payloads), that's a known MCP-class vulnerability pattern (cf. the documented SQL-injection-style bypass in the archived Postgres MCP server referenced above — the same class of "attacker-controlled data reaches a tool with insufficient sanitisation" problem applies to any MCP tool surface).
- **No audit-trail precedent** — a chat-based query interface needs its own logging/audit story (who asked what, when, what was returned) to satisfy the same four-eyes/chain-of-custody expectations discussed in Part 4; this doesn't come for free with MCP and would need to be built.

**Verdict**: reasonable as a **post-MVP, clearly-scoped, non-evidentiary bonus feature** (e.g. read-only dashboard-summary queries against aggregate/non-case-linked statistics) — not something to build into the core evidence-handling path in a 5-day hackathon. If demoed, demo it explicitly as "analyst convenience layer, air-gapped from evidence custody" so judges don't read it as a chain-of-custody hole.
